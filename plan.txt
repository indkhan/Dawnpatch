Dawnpatch: Technical Plan
Nov 21, 2026 · @Gyaat
Summary
Dawnpatch is an open-source, local-first tool that trains a developer's own open-weights coding model every night from their coding-agent history, on whatever machine they have (CPU only, a 6 GB laptop, a 24–80 GB GPU, a multi-GPU box or a DGX Spark), so it gets measurably better at their kind of coding. Dawnpatch is a working name.
It reads T3 Code, Claude Code and Codex history across all of the developer's projects, and is configured entirely through a small desktop app (Rust/Tauri) that shows what is being trained, live. While the machine is idle it turns the developer's sessions into episodes (the repo at a checkpoint, the prompt, the diff that was kept), trains a candidate model, tests it on recent work it never saw, and only replaces the current model if the candidate wins.
Goals
• Skill: the local model solves more of the developer's real tasks on the first try, in their repos, with their tests passing.
• Taste: it repeats fewer of the corrections the developer has already given.
• Trust: every promotion is backed by a held-out result, every version can be undone, and no chat replies, thinking or subagent calls are ever used.
Success criteria for v1
• On one developer's held-out T3 tasks, the trained model beats the base model plus the same memory (rules and retrieved past kept diffs in its prompt) on first-try pass rate, with a 95% confidence interval above zero.
• It loses no more than 1 point on a fixed general coding benchmark.
• The data audit shows zero chat, thinking or subagent text in any training set.
How to read this plan. The goals, data rules and evaluation gate are fixed. Everything else (models, methods, thresholds, tools, module boundaries) is a starting point. If the team tests something and it scores better on the evaluation harness, use it and update this plan.
Who it is for. Anyone can run it. Machines with large GPUs (24–128 GB, DGX Spark, multi-GPU) get the most from training; small GPUs and CPU-only machines run the same nightly loop with a smaller model, and for them most of the gain comes from memory. The 6 GB pilot laptop is a supported tier for small models.
Memory first, weights on top. Every tier gets memory (rules from corrections, turned into checks where possible, plus retrieval of similar past kept diffs). Training is the second layer and is only served when it beats the base model plus the same memory.
Principles and data rules
Dawnpatch learns from the developer's prompts, corrections, repos, tests and kept diffs, and never from the agents' chat replies, thinking or subagent calls.

Rules that do not change without a plan update
1.  Excluded data is dropped in the connector, before anything is written to disk. It is never stored, so it can never leak into training.
2.  Every record carries provenance at hunk or span level: author (developer, agent, own_attempt, repo, unknown), retention evidence (committed, survived_tests, next_checkpoint, rejected) and the objectives it may be used for (sft_target, preference_chosen, preference_rejected, fim, distill_context, input_only). The trainer refuses any example whose use is not in that list. A rejected or corrected hunk may only appear as the rejected side of a preference pair; unknown authorship counts as agent-authored.
3.  A role label is not proof of authorship. A message counts as typed by the developer only with source-specific evidence (T3 user_message item on a top-level thread with no parent thread or handoff origin; Claude Code user record that is not a tool result, not a sidechain and not injected by a hook or command; Codex event_msg UserMessage on a root session). Anything ambiguous (forwarded or delegated agent messages, handoffs, child threads, text pasted from an agent) is dropped in the connector before it is stored.
4.  Training on agent-written kept diffs is on by default (owner decision, 2026-11-21) and can be switched off in the app's Data screen, which states that each user is responsible for having permission from their providers. The developer's own diffs are always allowed.
5.  Everything runs on the developer's machine. No telemetry, no cloud, unless the developer chooses a remote GPU.
6.  A new model is used only if it passes the promotion gate. The previous version is always one command away.
Agent-written kept diffs being on by default does not change rule 2: if the developer switches them off, every hunk whose author is agent or unknown is excluded from all training objectives, including replay, preference pairs and teacher context for self-distillation (distill_context).
The current permission basis: the project owner was told by their providers that using diffs is fine as long as direct chat, thinking and subagent calls are not shared. Each user of the open-source tool needs their own confirmation. This is not legal advice.

Repo state per source
• T3 Code: checkpoints are git refs inside each project repo (refs/t3/orchestration-v2/checkpoints/.../ordinal/N). Restore with git worktree add --detach <tmp> <ref>. A read-only sample found about 91% of checkpoint refs still resolve; the rest are skipped.
• Claude Code: no checkpoints. Rebuild from the last commit before the session, overlay originalFile for touched files, verify by hash. Mark as lower confidence.
• Codex: no checkpoints. Use git by timestamp and keep the episode only if the first recorded patch applies cleanly.
• Evidence level is recorded on every start state: exact_tree (a recorded tree id or full manifest, e.g. a T3 checkpoint ref), touched_files_verified (touched files match by hash, the rest of the tree is assumed) or patch_applies (only the first patch applied). A patch that applies cleanly can apply to several commits, and untouched uncommitted files are unknown, so only exact_tree episodes may become held-out promotion tasks; the others are training-only with lower weight. All task counts (including the 50-task minimum) are measured after this filter and after verifier qualification.
Deduplication. T3 already contains Claude and Codex runs. When the Claude Code or Codex connector reads a session that T3 also recorded, keep the T3 version (it has checkpoints) and drop the duplicate by provider session id.
Scale seen in one developer's history (pilot): 1,106 T3 threads across 12–17 projects, 3,282 user messages, 4,716 file-change items, 2,172 checkpoints, 445 threads with checkpoints, 351 of them running tests or a typecheck. Enough to train adapters; not enough for a full retrain, and few projects means overfitting is the main risk.

When is a diff "kept"? In order of evidence strength: it is in a commit that reached the main branch or a merged PR (strongest); it survives unchanged to the thread's last checkpoint and tests pass there; it survives to the next checkpoint with no correction in between (weakest). A diff that a later turn reverted or that the developer corrected is labelled rejected. Weights per evidence level are a tunable starting point (1.0 / 0.7 / 0.4).
Storage. One SQLite file per user (episodes.db) plus content-addressed blobs for patches. Episodes are append-only and keep their source ids so any trained behaviour can be traced back to the examples that taught it.

Construction steps
1.  Select. Keep episodes with a restorable start state and a self-contained prompt. A prompt that only makes sense with the agent's reply ("do option 2") is dropped or, if the reference is to the developer's own earlier text, rewritten by the local model to stand alone.
2.  Keep the correction in its moment. Never merge a later correction into the original prompt; that hands the model hindsight it would not have had.
3.  Retrieve context from the prompt and the start-state tree only: files named in the prompt, the repo's import graph from those files, and a lexical search on the prompt, up to the context budget. Never use the kept diff, its touched files or anything after the start state to choose context, because at serving time those are unknown and on a held-out task they would point every contestant at the answer. The same retrieval is used at training, evaluation and serving time. E2 includes a test: deleting an episode's kept diff and end state leaves its evaluation input byte-for-byte identical.
4.  Find and qualify a verifier. Take test, typecheck and lint commands from package.json, Makefile, pyproject.toml or CI config. A task is eligible for scoring only if a trusted grader, run several times in a fresh sandbox, fails at the start state and passes at the kept end state with the same command and the same set of test identities each time (flaky tasks are excluded). The command, the test files, the config that selects tests (e.g. vitest/jest/pytest config, package.json scripts) and the expected test identities are frozen per task. Ineligible tasks are kept for training and reported separately, never scored.
5.  Generate synthetic tasks (required; the main training signal for skill): break-and-fix mutations of code with tests (flip a condition, delete a line, rename a call), and commit replays (reset to a commit's parent, its message is the prompt, its tests are the verifier).
6.  Dedupe. Near-duplicate prompts and retries of the same task stay together and in the same split.
7.  Scrub. Secrets scanner on every field; any hit drops the record. Only counts of hits (per rule, per project) are kept, never the matched value or its prefix.
8.  Audit. Assert that no field tagged as chat, thinking or subagent exists anywhere, and run an n-gram overlap check of every stored text field (prompts, corrections, rules, tool and command output, training targets) against the raw agent-message text the connector saw in that session, held in memory only during import. Any hit drops the record at import and fails the night if found later. The importer's tests include a forwarded agent message in a user-role envelope and a human prompt that quotes an assistant reply.
Splits. Episodes are assigned to dated cohorts per project before any dataset, rule or synthetic task is derived from them, and the assignment is permanent. Three splits: train; tune (used to pick methods, mixes and hyperparameters, and for experiments); promotion (used only by the promotion gate, never for tuning). Starting point: the newest 20% of threads per project are promotion, the 10% before them tune. Retries and duplicates follow their thread.
Lineage. Every dataset row, rule, synthetic task and replay example records the episodes and repo snapshots it came from. A held-out solution must not reach training by another route, so the following are excluded from training whenever they contain or descend from a tune or promotion episode: FIM spans from commits or checkpoints that include a held-out kept diff, commit replays of those commits, rules extracted from held-out corrections (they may still be used in the prompt for all contestants equally, but are frozen per comparison), and the weekly rebuild (it uses the train split only, never the whole store). E2 tests this with one fix that appears both in a held-out T3 thread and in a later commit. The memory retrieval index follows the same rule: for any task it may return only kept diffs from the train split whose episode ended before that task's start state, never the task's own thread, its descendants or later commits with the same fix. E2's leak test covers memory: deleting a held-out episode's kept diff and end state leaves the memory a contestant sees byte-for-byte identical.
Training stages and supported methods
Training runs every night, in stages that build on each other. Each stage is enabled only when it beats the previous one on the evaluation harness, and which stages run depends on the hardware tier (see Hardware tiers). Pilot lesson (2026-11-23): training a 2B model on one-shot prompt-to-diff examples taught the format, not the fix; with one developer's history alone (hundreds of usable edits) the training set is too small, so synthetic practice tasks from the developer's own repos are required, not optional.
1.  Stage 1, fill-in-the-middle on the developer's repos. Off by default in v1 (the product is an agent, not completion); switched on only if it wins on the harness. When on: learns their style, APIs and naming; starting point 10–20% of the training mix.
2.  Stage 2, supervised warm start on verified kept edits, in the serving format. Input: the request plus context retrieved from the start state (for large files, line-numbered windows around the relevant spans, never the whole repo). Target: the kept change as the harness's edit tool call in unified-diff form (in the pilot, unified diff beat SEARCH/REPLACE on a 2B model, which copied huge SEARCH blocks and ran out of tokens). Targets are rebuilt from git between checkpoints and verified by applying them, one per file per turn, never concatenated across turns, and dropped rather than truncated when too long. Correction examples weighted about 2x. Loss only on the target tokens.
3.  Stage 3, taste from corrections. First choice: on-policy self-distillation, where the teacher is the same model with the developer's correction or the kept diff in its context and the student sees the task without it (kept diffs written by Claude or Codex may appear in the teacher's context as demonstrations; their chat replies and reasoning never do). DPO (or ORPO/KTO) only on explicit pairs: a rejected or corrected diff against the kept one under the same request, plus the model's own passing vs failing gym attempts.
4.  Stage 4, practice in the gym, the main source of skill. Tasks: synthetic break-and-fix tasks from training-only snapshots of the developer's repos (keep only reproducible failing-to-passing tests), commit replays, and replayed real tasks from the train split. The model attempts each task K times (start with K = 4–8) in the real harness. Rejection-sampling fine-tuning on its own passing attempts comes first. GRPO with the verifier as reward runs only on the 80 GB+ / DGX Spark tier, and only for task families with mixed outcomes (0 < passes < K). When every attempt fails, give a hint from the kept diff (which files or function), retry, and train on its own success without the hint. Budget each night by completed, graded attempts, not by training steps.

Any model, no default (owner decision, 2026-11-21)
There is no default base model. The developer always picks one: any repo from Hugging Face or any model already on disk. Dawnpatch never refuses a model because of its architecture; it finds a way to train it, and only says "not trainable" after every fallback below has failed, with the reason.
Quantization is the developer's choice too. When they pick a model, the app lists its quantized variants on Hugging Face (for example bnb 4-bit, GPTQ, AWQ, FP8 and GGUF repos that name it as their base) next to the original, and a separate training precision control: 4-bit (QLoRA), 8-bit, or 16-bit (bf16/fp16). Any combination can be chosen; the compatibility check below says what it costs in memory and whether it works.
Compatibility check (runs when a model or quantization is picked, before any night uses it)
1.  Inspect. Read config.json and the file list: model_type, architectures, auto_map (custom code), quantization_config, parameter count, vocabulary size, context length, chat template.
2.  Pick a backend, fastest first. (a) Unsloth if it supports the architecture. (b) Otherwise plain transformers + TRL + PEFT, with bitsandbytes for 4- or 8-bit. (c) Otherwise the same with trust_remote_code for models that ship their own modelling code.
3.  Custom code is tied to library versions (the Nanbeige spike trained on one transformers version and failed to generate on it), so each custom-code model gets its own pinned Python environment, created with uv and recorded with the version.
4.  Custom code is code from the internet. Before using trust_remote_code the app shows the repo and files, asks once, and binds the consent to a digest of every executable file (including code referenced from other repos and code in local folders); any change asks again. Weights and code are downloaded and verified by a separate step with no code execution. Every process that loads custom code (dry run, training, evaluation, serving) runs isolated: a container (Docker in WSL2 on Windows, rootless Docker or Podman on Linux) with GPU access, read-only access to the approved model and the night's scrubbed inputs, one writable output folder, no network, no home folder, no credentials.
5.  Find LoRA targets. Use the known module names for the architecture; for an unknown one, target every linear layer except the embeddings and the output head.
6.  Dry run. Load the model, run two training steps at the chosen context on one real labelled example (checking that loss is masked to the target tokens and that the adapter changes the output on that example), save and reload the adapter, and do one tool-call round trip through the chat template and the intended serving path. Measure peak memory and pick the largest context that fits; reserved memory above the card's physical VRAM counts as not fitting, because the Windows driver silently spills into shared system memory and runs 30–100× slower instead of failing. Record the exact working combination (backend, precision, versions, context).
7.  Fallbacks when a step fails, tried in order and reported: Unsloth → plain PEFT; 4-bit fails on custom layers → 8-bit → 16-bit LoRA with gradient checkpointing and optimizer offload to CPU RAM; out of memory → shorter context → smaller batch with more accumulation; no chat template → ChatML, with a warning. A fallback that changes what the developer picked (precision, context, template) is shown and needs one click to accept before it is used.
8.  Already-quantized repos. GPTQ, AWQ and bnb 4-bit repos are trained with LoRA on top of the frozen quantized weights (PEFT supports these). FP8 is dequantized to bf16 if the GPU lacks FP8. A GGUF file cannot be trained: the app reads the base model named in its metadata and offers to download that original instead, or to dequantize the GGUF (lossy, with a warning).
9.  Result. The Model screen shows a badge (Unsloth, Standard, Custom code, or Not trainable with the reason), the measured memory and context, and which serving targets will work.
GPU ownership. On small GPUs serving, training and evaluation cannot share memory, so the app owns the GPU through one lease. The endpoint unloads idle weights after a few minutes; a night starts only after the server has unloaded; a foreground request during a night pauses the run (cooperative pause) and is served, and the run resumes when the machine is idle again; evaluation loads contestants one at a time. This cycle is part of the pilot-laptop acceptance test.
Serving any model. If the trained model converts to GGUF it is exported to Ollama, LM Studio and llama.cpp. If llama.cpp does not support the architecture (new or custom models), the stable endpoint is served by the built-in Python server (transformers, OpenAI-compatible) or by vLLM where vLLM supports it, and only the export targets that work are offered. The gym (stage 4) falls back from vLLM to transformers generation the same way; it is slower but still trains.
Starting hyperparameters (tune freely): LoRA rank 32–64, alpha 2x rank, learning rate 1e-4 to 2e-4 for SFT and 5e-6 for RL/DPO, 1–2 epochs over new data per night, effective batch 8–16, gradient clip 1.0.
Long contexts. Agent trajectories can exceed 30k tokens. Keep the head and tail of long tool outputs (about 2k tokens), drop old observations, and train per segment. The context budget is set by calibration on the user's hardware.
Anti-forgetting. Each night trains on new data plus a replay buffer of earlier accepted examples (starting point 30%), with a KL penalty to the base model in RL stages. Avoid public trajectory datasets for replay unless their provenance is clean.
Continual schedule. Training runs every night on every training tier (CPU-only nights are memory-only unless training is switched on); how often a new version may go live is the user's choice (see Promotion cadence). Each night continues the current candidate adapter. A full rebuild from the pinned base model runs weekly, when the base model changes, or after Forget, using the train split only. Episodes are the asset; weights are a cache.
Evaluation and promotion gate
A candidate model replaces the current one only if it beats the base model plus the same memory on the developer's held-out tasks without getting worse at general coding. The evaluation harness is built before any training (epic E2), because without it no improvement claim can be trusted.

Promotion rule (starting point, tune with evidence)
1.  Against the baseline: candidate pass@1 minus base + memory pass@1 has its interval's lower bound above zero on the promotion split, at the per-attempt level set by the cadence, using a paired bootstrap clustered by thread and project (related tasks move together, so they are resampled together). See Sequential testing under open questions: checking more often requires a stricter level.
2.  Against the incumbent: candidate pass@1 is at least the served version's (starting point: paired difference ≥ 0 and its lower bound above −2 points), and incumbent-pass/candidate-fail tasks are at most 2 or 3% of tasks, whichever is larger. On a tie the incumbent stays; a candidate identical to the incumbent is never reported as a promotion.
3.  Repeated-correction rate does not rise. If there are fewer than 10 eligible correction cases in the promotion split, this check is reported as "not enough cases" and does not block.
4.  General coding drops by no more than 1 point; tool-format errors do not rise.
5.  The data audit and the canary check for the night are clean.
6.  Minimum data: at least 50 eligible promotion tasks (exact_tree start state, qualified verifier); with fewer, report "waiting for more data" and do not promote.
7.  Promotion cadence (user setting). Every night (default), weekly, monthly, or "when the candidate wins by X points": the lower bound of the per-attempt interval for candidate minus served version is at least X points of pass@1. Promotions under nightly need larger gains than under weekly or monthly, so the app suggests weekly while the promotion split is small. The cadence only decides when promotion is attempted; rules 1–6 always apply, and training and memory updates still run every night.
Reports show paired win/loss counts next to every interval. Because the promotion split is only used for promotion and tuning happens on the tune split, the interval keeps its meaning across nights; the promotion split is refreshed with each new dated cohort, and the sequential testing rule (see Open questions, Sequential testing) is decided; E5 implements it.
These rules are enforced in the registry operation that moves the served pointer, not in the UI. A skipped, timed-out, underpowered or partial evaluation leaves the candidate pending with the missing evidence listed; no setting in the app or CLI can promote without it.
"No measurable change" and "inconclusive" are valid outcomes and are reported as such.
Anti-gaming. Each candidate patch is applied to a fresh copy of the start state and graded there with the task's frozen command, frozen test files and frozen test-selection config; changes the patch makes to tests, test config or the command are discarded before grading. The expected test identities must all run and pass; deleted assertions, skipped or missing tests fail the attempt. The verifier runs outside the model's view; the judge never sees the agent's chat or the kept diff when scoring rules. The judge's model, rubric and the approved rules are frozen per comparison. A patch that leaves the start state unchanged, or changes only files unrelated to the task, is a fail (the pilot evaluator counted such no-ops as applied).
Versioning and undo. Every candidate is stored with its base model, training config, dataset hash and example ids. The served model is a pointer; dawnpatch undo moves it back in one step. Keep at least the current and previous versions.
Nightly runtime, hardware and serving
The night runs only when the machine is idle, on power and the GPU is free, and it stops within seconds when the developer comes back, resuming from a checkpoint in the next idle window.
Night order: import new sessions → scrub and audit → update memory (rules, checks, retrieval index) → build datasets and synthetic tasks → generate gym attempts → train → evaluate → promote or reject → write the morning report. Generating attempts usually costs more than training, so the scheduler budgets generation first.
Scheduler. The desktop app's own scheduler loop; the app starts at login (Tauri autostart: Windows registry, macOS LaunchAgent, Linux .desktop) and sits in the tray. Headless installs can use the CLI under Task Scheduler, launchd or systemd instead. Idle detection from OS input-idle time plus "no agent traffic"; power and thermal checks; a memory guard that pauses or kills training under pressure. Configurable quiet hours.
Sandbox. Docker in WSL2 on Windows, rootless Docker or Podman on Linux. Dependencies are prepared without exposing the project: (1) a fetch step with network but no project source and no credentials downloads exactly the artifacts pinned in the lockfile from the public registries and verifies their hashes; (2) an offline, unprivileged, disposable container with a filtered snapshot of the repo (no .env, keys, credential files or git remotes) installs and builds from those artifacts, so lifecycle scripts run with no network. Attempts then run with network off, a CPU/memory limit and a wall-clock timeout. Cached images hold dependencies only, never project source. Projects whose dependencies cannot be prepared this way (no lockfile, private registries, network at build time) are reported and skipped. .env files and credential stores are never mounted.
Agent harness for the small model. A minimal loop with opencode-compatible tools: bash, read, write, grep, glob, plus apply_patch, which takes a unified diff and is the model's only edit tool (stage 2 trains on exactly this call; opencode's old-string/new-string edit is not offered, because that format looped in the pilot). The endpoint exposes the same tool to T3 Code and other agents. The model trains and serves with the same tool schema, so practice transfers to real use.
Hardware tiers (suggestions only, calibrated on first run). Every tier is supported and runs the same nightly loop; the tier changes the model size and which stages run. The tier only drives the suggestions shown in the Model screen and the Auto method; nothing is pre-selected. The developer can override every one of them in the app: any model, any method, any context. When a choice is unlikely to fit the measured memory, the app shows a warning with the estimate and lets them run it anyway; a run that runs out of memory stops cleanly and says so in the report.

Privacy and security
Nothing leaves the developer's machine by default, and anything sensitive is removed before it is stored, because a secret that reaches training can be memorised into the weights.
• Read-only sources. Connectors open app databases and logs read-only (mode=ro, no locks held) and never modify T3 Code, Claude Code or Codex files. Checkpoint restores happen in temporary worktrees, never in the developer's working copy.
• Projects on by default, off with one switch. All detected projects are imported unless the developer switches one off in the app's Data screen. Switching a project off stops new imports; choosing Forget removes it as described below.
• Secret scrubbing. gitleaks-style rules plus entropy checks on every field (prompts, diffs, command output, file contents). A hit drops the record, not just the string. .env, key files and credential stores are never read.
• Memorisation check. Real secrets are never kept, so they cannot be probed. Instead Dawnpatch generates random canary strings, inserts them at known points in a small number of training rows (recorded in a separate local file), and after training checks locally whether the model completes any canary from its prefix; any exact completion fails the night. A pass shows that this run did not memorise inserted strings at that exposure; it does not prove that no real secret was learned, which is why scrubbing before storage is the main defence.
• Sandbox isolation. No network during attempts, no host mounts beyond the temporary worktree, resource limits, timeouts.
• Data at rest. The data folder is user-only (0700 on Unix, user ACL on Windows). Optional encryption with an OS keychain key.
• Forget. Every derived artifact (patch blobs, dataset rows, rules, replay buffer entries, checkpoints, adapters, reports, sandbox images, caches) records which projects and episodes it depends on. Forget deletes the episodes and every artifact that depends on them, cancels queued and in-flight runs that used them, and schedules a rebuild from the pinned base (continuing the current adapter would carry the project along). Versions trained on the forgotten data are listed; the developer chooses to purge them or keep them, and kept ones are marked as containing forgotten data. Exports already copied to Ollama or LM Studio are listed as outside Dawnpatch's control.
• No telemetry. No account, no analytics. Remote GPU training is explicit opt-in and shows exactly what is uploaded; it is not in v1 (decided 2026-11-21) and comes after M2.
• Supply chain. Pin dependencies, verify downloaded tools (llama.cpp binaries, model weights) by checksum, and never execute code from the episode store outside the sandbox.

How the app runs the night
• The app starts at login, hidden in the tray. Closing the window hides it; training continues.
• Its scheduler loop checks the Schedule conditions every few seconds (idle time, AC power, GPU use via NVML, time window). When they hold it runs the night order below, one step at a time.
• The trainer is a Python child process. The app sends commands on its stdin and reads JSON lines from its stdout (stage, step, loss, eval loss, learning rate, tokens per second, current episodes, log), stores them, and pushes them to the UI.
• Every run has a durable id and a lease in the settings store, shared by the app and the CLI, so only one owner runs it and a crashed owner's run can be found and cleaned up.
• Pause is cooperative: on "pause" the trainer stops at the next step boundary, saves a checkpoint atomically (write to a temp folder, then rename), reports "paused" and exits, which frees GPU memory. Steps are sized so this fits the 10-second target; if a checkpoint is still writing, the app waits for it rather than corrupting it. A trainer that does not stop within the grace period is killed with its whole process tree (Windows Job Object, Unix process group), and the run resumes from the last complete checkpoint.
• Work inside WSL2 and Docker is supervised there too: each run's containers carry its run id label and are stopped by label; WSL-side workers are tracked by pid file inside WSL. On app start, anything labelled with a run that is no longer active is stopped. Unrelated WSL and Docker workloads are never touched. Tests cover user return, app crash and sleep/resume during training and during grading.
• The Python environment is created on first run with a bundled uv from a pinned lockfile, matched to the detected GPU and driver; the installer itself stays small. Models that ship custom code get their own pinned environment.
• Within a night the trainer process stays alive across stages (loading and quantizing took 2–3 minutes per start in the spike), and tokenized datasets are cached.
• Model downloads never rely on Hugging Face cache symlinks (they fail on Windows without Developer Mode): files are downloaded as plain files, limited to weights, config, tokenizer and code.
Terminal use (no app needed)
The desktop app is optional. Anyone with the codebase can do everything from a terminal, without downloading or installing the app: clone the repo, build the CLI, and run it. The app and the CLI are two front ends over the same Rust core crate (settings store, scheduler, trainer control, registry, endpoint); the CLI binary does not depend on Tauri or a webview, so it also works on servers and over SSH.
• From source: git clone, then cargo run -p dawnpatch-cli -- <command> (or cargo install --path crates/cli to get a dawnpatch binary). The CLI creates the Python trainer environment with uv on first use, exactly like the app.
• Parity rule: every action and every setting in the app has a CLI equivalent, and the reverse. CI checks this against the settings list in ui/DESIGN.md.
• Settings from the terminal: dawnpatch config list / get <key> / set <key> <value> (same keys as ui/DESIGN.md), plus optional config export/import to a file. No file has to be edited.
• Watching from the terminal: dawnpatch watch streams the live run (stage, step, loss, eval loss, GPU, VRAM, temperature) as text, with --json for the raw JSON lines.
• Scheduling without the app: dawnpatch daemon runs the same scheduler loop in the foreground; dawnpatch daemon install registers it as a user service (Task Scheduler on Windows, systemd user unit on Linux).
• The app and the CLI can be used together on one machine: both read the same settings store and take the same run lease, so they never start two runs at once.

Pilot results (2026-11-22/23, 6 GB laptop, MiniCPM5-2B, 4-bit QLoRA)
• Run 1 (experiments/t3-minicpm5): input was the request plus a file name only, targets were raw provider diffs in mixed formats, 21% truncated. Held-out loss fell (1.91 to 1.47) while generations invented file contents and looped. Lesson: loss is never evidence; the model must see the code it edits; targets must be clean.
• Run 2 (experiments/t3-minicpm5-v2): request plus the touched file from the T3 checkpoint, targets rebuilt from git and verified, non-self-contained prompts dropped. Only 144 training edits survived. On 12 held-out edits, the unified-diff adapter's edits applied 75% of the time vs 17% for the base; SEARCH/REPLACE looped; the unified-diff adapter still ran away on 33% of edits; no exact matches, several applied patches were no-ops, and the interval came from only 4 thread clusters. Lessons: unified diff is the better target at 2B; the evaluator must fail no-ops; one developer's history is too small to train skill on, so synthetic tasks are required; real held-out tasks need running tests, not similarity scores.
• Reviews (Claude Opus 5.5, GPT-6.2 Astra, 2026-11-23) agreed: build the replay harness and memory first, design for big machines while keeping every tier supported, and keep training only where it beats base + memory by a predeclared margin (starting point: 5 points pass@1; a research kill criterion, not a gate rule) without a general-coding drop.
Experiments and open questions
The team owns these choices: run the experiment on the evaluation harness, keep whatever wins, and record the result here.
How to change the plan
1.  Write the hypothesis and the metric it should move.
2.  Run it against the current default on the same held-out tasks, with the paired bootstrap.
3.  If it wins without breaking a guardrail, make it the default and add a one-line entry to the decision log below.
4.  Fixed points that need the project owner to sign off: the data rules, the held-out split and the promotion gate's guardrails.
